# Цифровий двійник сесії (session replay twin): сценарії рушія -> збурення каналу -> справжнє ПЗ проєкту

Станом на 2026-10-03. Код: `tests/sim/twin/` (`twin.py`, `schedule.py`, `channel.py`, `harness.py`, `analysis.py`, `contracts.py`, `test_twin.py`, `run.sh`, `mutate.sh`). Власність цього документа й каталогу: лише вони; жоден існуючий файл проєкту не змінено. Запуск перевірки: `tests/sim/twin/run.sh --check` (офлайн, ~7 с). Безпека: усе йде лише через loopback UDP, міст стартує з `--confirm-props-off`; **не підключати до реального апарата** (`AGENTS.md` §3).

Позначки достовірності: **REPO** (перевірено в репозиторії, `файл:рядок` або команда), **SRC** (першоджерело; тут лише через існуючі документи репозиторію, мережею не ходив), **INF** (мій висновок), **HW** (лише залізо), **UNVERIFIED**, **SYNTH** (синтезоване значення для планування, не факт), **RUN** (команду запущено в цій сесії, вивід наведено).

**Коротко.** Двійник бере одну сесію стохастичного рушія (`scenario_engine.py events --seed N`, ті самі події, перевіряється тестом), детерміновано перетворює її на розклад збурень каналу (повна тиша при відвалі USB-адаптера й тепловому вимкненні, затримка запуску, пакетні завади, спади шуму, затримка від зупинок) і **прикладає цей розклад до справжніх програм**: `bench/tx12_bridge.py` (dead-man, single writer), `tests/sim/apm_fc.py` (модель failsafe ArduPilot) і `tests/sim/udp_probe.py` (потік «відео»). Міряє системні наслідки: скільки секунд RC без керування, коли спрацювали GCS/radio failsafe, чи відпустив міст канали, заморозка відео, час до відновлення, розбіжність прогнозу рушія з поведінкою програм. 15 контрактів на порогах перевіряються на кожному прогоні й у тестах (66 тестів, 20 мутацій із 20 вбито).

| Компонент | Справжній? | Роль у двійнику |
|---|---|---|
| `bench/tx12_bridge.py` | так, процес без змін (`--input stdin`) | dead-man, throttle failsafe, release, silent, single writer, heartbeat (REPO `tx12_bridge.py:429-436`) |
| `tests/sim/apm_fc.py` + `apm_model.py` | так, процес; **це МОДЕЛЬ ArduPilot, не автопілот** | RC_OVERRIDE_TIME, FS_GCS, radio failsafe |
| `tests/sim/udp_probe.py` | так, процес | потік «відео» і лічильники delivery |
| `tests/sim/air_relay.py` | **ні, не в основному шляху** (див. нижче) | правило рішення продубльоване в `channel.decide`, звіряється тестами |
| `tests/sim/video_latency.py` | **не запускався**: `python3 -c "import gi"` дає `ImportError` (RUN), потрібен системний `python3-gi` | відео моделюється як рівномірний UDP-потік, без кодека |
| канал | **SYNTH/UNMEASURED** | усі параметри з пріорів рушія |

**Чому не сам `air_relay.py`.** Він ретранслює сирі кадри 802.11 між veth (AF_PACKET, потрібен root) і не несе UDP-MAVLink; розклад лише через аргументи на запуск, тиші немає (REPO `air_relay.py:62-65`, вхід `AF_PACKET`). Тому `channel.py` — непривілейований UDP-хаб із **тим самим правилом рішення**: один `rnd.random() < loss` на кадр, далі `max(0, gauss(delay, jitter))` для вцілілих, пакети за часом доставки (`channel.decide`). Захист від дрейфу: (а) тест читає `air_relay.py` і вимагає ті самі вирази; (б) `TestAirRelayCrosscheck` під root із veth запускає **справжній** `air_relay.py` з `--loss 0.3 --seed 5` і вимагає, щоб множина доставлених кадрів збігалася з `decide()` на тому ж seed (RUN: проходить як root; під `nobody` SKIP). Тиша = loss 1, тож споживання RNG збігається з `air_relay --loss 1`.

### 2.1 Стиснення часу (чесно)
Справжні програми працюють у реальному часі, тому «стиснення» зроблено трьома окремими механізмами, кожен звітується в JSON (`plan`):
1. **Вирізання тиші**: між «поганими» вікнами модельний час викидається (`elided_model_s`); програми бачать лише коротку чисту паузу (`quiet_s`) і прогрів (`warmup_s`, 3 реальні с: міст вчить sysid FC з його heartbeat).
2. **Обрізання довгих тихих інтервалів** до `silence_cap_s` = `max(FS_GCS_TIMEOUT, RC_OVERRIDE_TIME+RC_FS_TIMEOUT)+2.5` модельних с (`truncated_model_s`). Після цього всі пороги failsafe вже перейдено, тож стан «без керування» вважається сталим; **довжина понад обрізання екстраполюється, а не вимірюється** (INF, поле `extrapolated.note`).
3. **`--speed X`**: тривалості розкладу й часові константи моделі FC (`RC_OVERRIDE_TIME`, `FS_GCS_TIMEOUT`, `RC_FS_TIMEOUT`), dead-man і період heartbeat моста діляться на X. Межа 1..2 не довільна: реєстр моста має жорсткі межі `TX12_DEADMAN_MS >= 50`, `TX12_RELEASE_HOLD_S >= 0.5`, `TX12_HB_PERIOD_S >= 0.2` (REPO `config/registry.tsv:11,18,21`), їх обхід вимагає `--i-know`, а двійник не обходить. **Висновки для звіту брати із `--speed 1`**; `--speed 2` це швидкий режим для матриці й CI.
4. **Бюджет** `--budget`: якщо план довший, відкидаються вікна з найменшим балом (при рівності пізніші), це видно в `plan.skipped`. Завжди лишається не менше `steady_min_s` (5 с) чистого каналу для статистики втрат.

Облік перевіряється тестом: `replayed_model_s + elided_model_s + truncated_model_s = модельна тривалість сесії`.

## 3. Як події рушія стають збуреннями (SYNTH)

| Подія рушія | Збурення каналу | Примітка |
|---|---|---|
| `bringup` (t=0, ok) | тиша `[0, t_s_total)` | «затримка запуску»; `ok:false` = тиша до кінця |
| `usb_drop` ... `usb_return` | тиша від drop до `return + t_bringup` | повернення адаптера й повторний bring-up; `t_bringup` береться з першого `bringup` (INF: рушій не друкує другий) |
| `usb_latched` / `usb_stuck` | тиша до кінця сесії | |
| `thermal_shutdown` ... `thermal_resume` | тиша | AIR-адаптер вимкнений |
| `burst_on` ... `burst_off` | втрата = залишкова втрата моделі при `burst=True` | через `dm.link_eval` + `residual_of` |
| `shock` (excess_db) | втрата з експоненційним спадом `proc.shock_tau_s` (кроки 1 с) | та сама модель |
| `stall` (backlog_ms) | додаткова затримка `backlog` на `backlog/catchup` с | |
| фон | втрата = залишкова втрата ідеального стану, затримка/джитер з `relay_from_model.segment` | |
| `throttled`, `undervoltage`, `thermal_derate`, `usb_trip`, `creep_reset` ... | **не застосовуються** (лічаться в `model.events_not_applied`) | `usb_trip` супроводжується `usb_drop`; решта не змінює канал в цій моделі |

Припущення, які НЕ є фактами: канал симетричний (uplink = downlink, INF/UNVERIFIED); USB-адаптер GS єдиний радіотракт (drop = тиша в обидва боки); TX12 на тому ж обмежувачі живлення Pi 5 лише при `--joystick-usb shared` (для Pi 5 «спільний запобіжник чи на порт» документами не встановлено: **UNVERIFIED**, `docs/SIM-MODELS.md:188`); за замовчуванням джойстик незалежний.

## 4. Що міряється

Усі часи в реальних секундах від старту плану (канал). Кожен вихід `analysis.analyze`:

- **RC без керування**: час, коли оператор «рухає стіки» (подача не зупинена), а FC не бачить override (за EVENT `RC override started/expired` від `apm_fc.py`); окремо «час до першого керування» (startup).
- **Failsafe**: коли спрацювали `RC override expired`, `GCS Failsafe`, `Radio Failsafe` відносно початку тиші, і коли очистилися (через oracle).
- **Міст**: чи відпускав канали (кадри throttle-failsafe → release → тиша), що сказав його журнал (`DEAD-MAN`, `input fresh`, `release hold done`), sysid і target кожного кадру (зняті на вході хабу, до збурень).
- **Відео**: послідовність пакетів `udp_probe.py` з часами; «заморозка» = інтервал між доставленими пакетами > 0,25 с (**SYNTH**), час до відновлення після повернення каналу.
- **Oracle** (`apm_model.ApmModel` на віртуальному годиннику, на доставлених кадрах) проти реальних EVENT `apm_fc.py`: перевіряє саме обгортку-процес (цикл 5 мс, фільтр target, події).
- **Прогноз проти реальності**: аналітичний прогноз per-outage (чи мало б спрацювати expiry/GCS/radio failsafe за довжиною тиші) проти виміряного; сумарні `down_s` рушія проти тиші з подій.

## 5. Контракти на порогах

Кожен контракт це `fn(result, P, ctx) -> PASS|FAIL|NA`; пороги з констант самого ПЗ, інші з таблиці `contracts.TOL` (**SYNTH**, позначені).

| ID | Інваріант | Поріг | Клас |
|---|---|---|---|
| K01 | кожен RC override має sysid моста, `MAV_GCS_SYSID` FC == sysid моста, FC не ігнорував overrides | точно | safety |
| K02 | RC override адресований лише sysid FC | точно | safety |
| K03 | під час тиші через хаб не пройшов жоден пакет | 0 | hub |
| K04 | після прогалини > RC_OVERRIDE_TIME FC скидає override (не раніше і не без прогалини) | -0,1 с .. +0,45 с | safety |
| K05 | FS_GCS_ENABLE=1: GCS failsafe не пізніше FS_GCS_TIMEOUT після останнього heartbeat (+0,45 с); без прогалини не спрацьовує; при 0 не спрацьовує | +0,45 с | safety |
| K06 | лише override (без приймача): Radio Failsafe через RC_OVERRIDE_TIME+RC_FS_TIMEOUT | +0,45 с | safety |
| K07 | `apm_fc.py` поводиться як `ApmModel` на доставлених кадрах | 0,2 с | model |
| K08 | керування відновлене після повернення каналу | <= 1,0 с (**SYNTH**) | recovery |
| K09 | відео «заморожене» на всю тишу (>= 90 %) і повертається | <= 1,0 с (**SYNTH**) | recovery |
| K10 | лічильники `udp_probe.py` == касета хабу | +-3 | hub |
| K11 | секунди RC без керування == прогноз `max(0, L-RC_OVERRIDE_TIME)` | відновлення +0,5 с (**SYNTH**) | divergence |
| K12 | аналітичний прогноз прапорів failsafe == реальні програми | смуга неоднозначності біля порога | divergence |
| K13 | dead-man: після втрати джойстика throttle failsafe, release, тиша, відновлення | вікно 0,1..0,4 с, hold +0,4 с | safety |
| K14 | `down_s` рушія пояснюється тишею з подій | `dt*(n+1)` (квантування зрізів) | divergence |
| K15 | прогін вкладається в бюджет | точно | plan |

Вихідний (початковий) інтервал `bringup` не оцінюється K08/K09/K11/K12 (немає стану «до»), його затримка до першого керування звітується окремо.

**Варіації того самого сценарію** (`pi5_3a_weak_psu --seed 1`, `--speed 2`):
- `--fs-gcs-enable 0`: контракти PASS; GCS failsafe не було взагалі (колонка порожня), радіо failsafe спрацював, бо приймача немає. Підтверджує `docs/MAVLINK-ROUTER.md:100,109` (типово 0, потрібно виставити вручну) лише на моделі.
- `--joystick-usb shared`: на USB-тріпі міст отримав «зникнення джойстика», `DEAD-MAN` спрацював 2 рази, `RC без керування` впало до 0,09 с (оператора немає, нема чого втрачати); перша версія контрактів тут давала два хибних FAIL (K11, K13), виправлено (`ends_in_run`, виняток для `+joystick`).
- `--mav-gcs-sysid 254` (хибна конфігурація FC): **K01, K04, K06, K11, K12 FAIL**: FC ігнорує overrides (`override from sysid 255 ignored`, 105 подій), керування не встановилось ніколи (`startup never`), GCS failsafe не армується. Тобто двійник виявляє помилку `MAV_GCS_SYSID` (`docs/MAVLINK-ROUTER.md:94-96,110`).

## 7. Знахідки

Дефектів у **коді проєкту** (`tx12_bridge.py`, `apm_fc.py`, `apm_model.py`, `udp_probe.py`, `air_relay.py`) двійник не виявив: усі контракти зелені на матриці й на реальних константах; код не змінювався. Спостереження, які варто знати (клас: проєкт / рушій / двійник):

1. **Міст не знає про втрату каналу (INF, за дизайном).** Під час тиші `DEAD-MAN` не спрацьовує, міст продовжує слати стіки в мертвий канал (RUN `bridge.frames_by_class` при `--speed 1`: STICK 516, FSTHR 0, RELEASE 0 за 32 с), а скидає override лише FC через RC_OVERRIDE_TIME (`I1` у виводі). Dead-man захищає від втрати джойстика, не радіоканалу. Це збігається з коментарем у `tx12_bridge.py` (шапка), але означає, що **захист від втрати лінка повністю лежить на параметрах FC** (`RC_OVERRIDE_TIME`, `FS_GCS_*`), які двійник моделює, але не доводить.
2. **GCS failsafe за heartbeat спирається на 1 Гц heartbeat моста** (`TX12_HB_PERIOD_S` 1 с, `tx12_bridge.py:410`) і поріг 5 с: GCS failsafe спрацьовує від 4 до 5 с після початку тиші залежно від фази heartbeat (RUN: 4,02 с). Для пакетних завад із втратою ~80 % п'ять поспіль загублених heartbeat не виключені; частота хибних спрацювань у польових завадах **UNVERIFIED** (канал SYNTH).
3. **Час до першого керування після запуску ~1 с понад bring-up** (RUN: від 0,2 до 0,96 с після кінця bring-up, залежно від фази heartbeat FC): міст чекає heartbeat FC (`apm_fc.py:76` 1 Гц) перед першим кадром. Після відвалу адаптера міст зберігає `target`, відновлення швидке (0,01-0,09 с). Реальний ArduPilot шле heartbeat також 1 Гц (INF), тож порядок величини переноситься, число ні.
4. **Рушій: `down_s` це квантовані зрізи й не включає bring-up.** `nominal_pi5_5a_150m` seed 1: рушій `down_s=20 с` (dt=20 с), події дають 7,35 с (D1); не помилка, але порівнювати з вимірюваним слід по подіях, а не по `down_s`. К14 допускає `dt*(n+1)`.
5. **Рушій: `down_s=0` не означає «канал працює».** `elrs_usb3_desense_edge` seed 3: `down_s=0`, але фонова втрата 1,0 (край дальності): реальні програми за 10 с так і не встановили керування (міст не дочекався жодного heartbeat FC). `availability=0` цю ситуацію показує, `down_s` ні.
6. **`air_relay.py` не імпортується як бібліотека**: правило рішення вбудоване в `main()` (REPO `air_relay.py:62-65`), немає розкладу й тиші. Двійник дублює правило і сторожить його двома тестами. Рекомендація (не виконувалась): винести `decide()` у функцію й додати розклад.
7. **`udp_probe.py` у рядку `PROBE` друкує `sent=a.count` (заплановане), а не фактично надіслане** (REPO `udp_probe.py:82`); двійник тому звіряє з касетою хабу, яка рахує фактичне. Для штатних запусків без обриву збігається.
8. Чого двійник не встиг показати як дефект, бо це моделі: поведінку реального `EvdevSource` (REPO `tx12_bridge.py`, потік оновлює `ts` навіть без подій: зависання USB без помилки читання може не запустити dead-man) двійник **не перевіряє**: він використовує `--input stdin`. **UNVERIFIED**, лише HW.

Помилки самого двійника, знайдені й виправлені під час розробки (чесно): «поганий» інтервал визначався абсолютною втратою (на краю дальності вся сесія ставала одним «поганим» інтервалом: тепер відносно базової втрати); «тиха» втрата рахувала й вікна з пакетною завадою; `K13` вимагав відновлення стіків, коли зупинка триває до кінця прогону; мутація M9 спочатку виживала (див. вище).

## 8. Що двійник доводить і чого НЕ доводить

**Доводить (L1: логіка + реальний код у пісочниці).**
- Події рушія детерміновано за seed стають розкладом (дайджест `schedule_digest`), без приватної реімплементації рушія (тест звіряє з `scenario_engine.py events`).
- Справжній `tx12_bridge.py` за втрати джойстика видає throttle-failsafe, release, мовчання, потім відновлюється; шле лише зі своїм sysid і лише на sysid FC.
- `apm_fc.py` відтворює `ApmModel` (K07) і спрацьовує в межах порогів (K04-K06) при відвалах заданої довжини.
- Прогноз за довжиною тиші (K11, K12) збігається з реальними програмами; розбіжності між рушієм і програмами виводяться (`D*`).

**НЕ доводить.**
- **Канал SYNTH/UNMEASURED**: усі втрати, затримки, пороги бурст/шок, довжини bring-up походять із пріорів `params.degrade.json`, не з вимірів (`docs/SIM-SCENARIOS.md`, розділ чесності). Двійник «пропускає» їх крізь справжній код, але не робить їх виміром. Відсоткові ймовірності спрацювання failsafe у польоті звідси брати не можна.
- **ArduPilot**: лише `apm_model.py` (власне правило проєкту з позначками SRC/SITL/INF), не прошивка Matek H743 і не SITL; фактичні таймінги ArduPilot можуть відрізнятися (у `apm_model.py` зазначено: SITL міряв спливання override 2,8 с при 3 с). **ELRS/CRSF** не змодельовані, `receiver_present=False` це найгірший випадок («лише wfb-ng»); у реальному контурі ELRS основний канал, а override лише резерв (`AGENTS.md` §3).
- **Радіо й залізо**: не доводить поведінку RTL8812EU/AU, драйвера, USB Pi 5, живлення, реальних затримок wfb-ng (FEC, перемежування), реальний `video_latency.py`/кодек/заморозку картинки (відео це UDP-потік 150 пак/с, «заморозка» = пропуск доставки > 0,25 с, **SYNTH**).
- **Симетрія й одноканальність**: uplink = downlink (INF); один потік MAVLink без mavlink-router; фільтрація sysid лише в моделі FC.
- **Час**: це не прогін 600 с. Лише вікна навколо поганих інтервалів, довгі тиші обрізано до `silence_cap_s` і екстраполовано; `--speed 2` змінює відношення констант до фіксованих часових величин моста (hold, період циклу): висновки з `--speed 1`. Loopback на завантаженій машині дає похибки порядку десятків мс (контракти мають запас 0,2-0,45 с); при сильно завантаженому CPU результат може коливатися.
- **Безпека польоту**: нічого з цього не замінює стендових перевірок без гвинтів (`docs/STATUS.md`, `docs/BENCH-HARDWARE.md`); результати не мають тегів HW.
