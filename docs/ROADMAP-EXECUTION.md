# План виконання: закриття прогалин і шлях до інженерного пакета

Станом на 2026-10-02 (оновлено; CI зелений на b3597da). Спирається на `docs/GAPS.md` і три проєктні опрацювання (Фаза 1, збірка/CI, паритет функцій/`gs-mavlink`), чиї якорі `файл:рядок` я перевірив у коді.
Позначки: **✔** перевірено мною, **аудит** з відповіді агента без окремої перевірки, **UNVERIFIED** не підтверджено, **HW** лише на залізі.
За вашою вказівкою юридичні й регуляторні питання в план **не входять**. Фізична безпека (гвинти, батарея, ESC) лишається, бо без неї тест RC небезпечний.

## 1. Принципи (щоб рух був органічним)

1. **Нуль зміни поведінки Radxa.** Кожен PR на `gs/`/`build/` доводить, що вихід скриптів ідентичний до рефакторингу (golden-тести), і лише потім додає Pi.
2. **Спершу тест, потім зміна.** «До»-еталон знімається з незміненого коду до першого рефакторингу.
3. **Малі зворотні PR.** Один PR = одна підсистема, зелений CI, відкат одним `revert`.
4. **Дві паралельні колії**, що не блокують одна одну:
   - **Колія S (software):** рефакторинг, тести, збірка. Виконується без заліза.
   - **Колія H (hardware):** прогін стенду `bench/` на реальних Pi за `docs/GUIDE.md`. Не залежить від колії S, бо стенд працює на стандартній Pi OS. Її результати знімають позначки HW і задають параметри для колії S.
5. **Кожне твердження про Pi має статус** (SRC/INF/HW); у код потрапляє лише підтверджене.

## 6. Критерії «реального інженерного пакета»

1. CI зелений на кожному PR: shellcheck без нових зауважень (ratchet), loopback, тести golden.
2. Збірка відтворювана: усі завантаження закріплені, є маніфест версій в образі.
3. `BOARD=radxa-zero3` дає ідентичний образ і поведінку; `BOARD=rpi4` збирає завантажуваний образ.
4. Безпечні дефолти з явним opt-in для застарілої поведінки.
5. Стенд на залізі пройшов T1–T8, R1–R6; результати в репозиторії; позначки HW у `docs/` знято.
6. `gs-mavlink` з одним писачем RC, dead-man і обнуленням при втраті.

## 7. Що я не знаю й що треба перевірити першим

- Прапорці й синтаксис `mavp2p`: **SRC-підтверджено** за README/кодом (`udps/udpc/udpb/tcps/tcpc/serial`, `--hb-systemid`), див. `docs/MAVLINK-ROUTER.md`; лишаються UNVERIFIED імена релізних активів (403) і поведінка на реальному FC; mavp2p не має фільтрів, єдиний писач RC забезпечувати через `MAV_GCS_SYSID` чи `mavlink-router`.
- Чи має SITL прийнятну швидкість збірки/роботи на Pi 4 (не виміряно); SITL не відтворює втрату RC-лінка для `FS_THR`, потрібен реальний FC.
- Чи завантажується образ за схемою спайку на Pi 4/5 і чи працює overlayroot (HW).
- Чи WiFi-AP режим онборд-чипа Pi працює паралельно з monitor-інтерфейсом (не перевірено).
