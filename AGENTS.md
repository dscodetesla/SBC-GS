# AGENTS.md: правила для будь-якого агента в цьому репозиторії

Короткий операційний посібник для людей і ШІ-агентів (Claude Code, субагенти, інші). Джерело істини про факти: `docs/KNOWLEDGE.md`; поточний стан: `docs/STATUS.md`; пам'ять проєкту: `MEMORY.md`; контур і критерії готовності: `docs/CONTOUR-AIR.md`, `docs/CONTOUR-GS.md` (коли існують).

## 1. Що це за проєкт
Форк збірника образу наземної станції OpenIPC для Radxa Zero 3W; триває порт на Raspberry Pi 3B+/4/5. Кінцевий результат: **працюючий контур AIR<->GS** (відео 720p, телеметрія MAVLink, безпечний резервний RC), зібраний як відтворюваний інженерний пакет. Не лабораторна обв'язка навколо нього.

## 2. Дисципліна доказів (обов'язково)
- Кожне твердження про світ має тег **SRC** (прочитано першоджерело, є URL), **REPO** (перевірено в цьому репозиторії/CI, є `файл:рядок` чи команда), **SNIP** (з фрагмента), **INF** (висновок), **HW** (можливо лише на залізі), **UNVERIFIED** (не підтверджено), **SYNTH** (синтезоване правдоподібне значення для планування, НІКОЛИ не факт).
- Ключові цитати перечитувати напряму (`curl https://raw.githubusercontent.com/...`), не лише з підсумків `WebFetch`.
- Не обходити політику мережі (403/407), не вимикати TLS, не знімати `HTTPS_PROXY`. Якщо хост заблоковано, так і писати.
- Не видавати модель за вимір, а простір симуляції за доказ на залізі (див. `docs/SIM-BLOCKERS.md`).

## 3. Безпека (фізична й функціональна)
- Тест RC лише без гвинтів, з від'єднаними батареєю й ESC; FC живиться від USB.
- `bench/gs_mav.py`, `bench/fake_fc.py`, `tests/sim/apm_fc.py`, `tests/sim/sitl_probe.py` не підключати до реального апарата з гвинтами.
- RC через wfb-ng не може бути єдиним каналом: основний `TX12 -> ELRS TX -> ELRS RX -> FC`; wfb-ng RC override лише резерв. Один писач RC (`bench/tx12_bridge.py`), `MAV_GCS_SYSID` на FC має дорівнювати sysid моста.
- Значення, що впливають на безпеку польоту (dead-man, ліміти, failsafe), мають жорсткі межі в реєстрі конфігурації; зняти їх можна лише явним прапорцем із гучним логом.

## 4. Розподіл праці (делегування)
1. Керівний агент (lead) формулює завдання, дає **неперетинні файли-власність** кожному субагенту і **забороняє** йому `git commit/push/checkout` та створення PR.
2. Субагент повертає звіт із реальними результатами команд (числа, не оцінки) і списком UNVERIFIED.
3. Lead **сам повторно перевіряє** (тести під root і під `nobody`, `shellcheck`, ratchet, діф `gs/`+`build/`, вибірково першоджерела) і лише тоді коміть. Звіт субагента не є доказом.
4. `git add` лише перевірені файли: `git add -A` під час роботи інших агентів заносить недописані файли. Після коміту `git show --stat`.
5. Незалежний аудит робить окремий агент зі свіжим контекстом (`docs/AUDIT-INDEPENDENT-*.md`); самооцінка не вважається незалежною.
6. Не приймати «обхід замість виправлення» (приклад: підганяння тексту маркера, щоб не міняти golden).

## 3a. Перевірка перед комітом (мінімум)
Одна команда відтворює CI-джоби `lint` і `golden`: `tests/precommit.sh` (лише лінт: `--quick`). Запускати **перед кожним комітом** (пропуск ratchet вже зламав CI: SC2163 у `release.sh`, 2026-10-03). Нижче те, що вона виконує, плюс перевірки поза нею:
```
tests/run.sh                         # golden + static (усе ok)
# те саме НЕ під root: копія в /tmp (не в /tmp/claude-0: права 0700), chown -R nobody:
setpriv --reuid=65534 --regid=65534 --clear-groups env HOME=/tmp TMPDIR=/tmp tests/run.sh
shellcheck -x -S warning tests/*.sh tests/lib/*.sh tests/static/*.sh tests/sim/*.sh build/lib/*.sh gs/lib/*.sh gs/boards/*.sh gs/mavlink/*.sh
tests/shellcheck-ratchet.sh          # нових зауважень немає
PY=<venv з pymavlink==2.4.50> tests/sim/smoke.sh
cd bench && PY=<той самий venv> ./bench.sh loopback
```
Мутаційні перевірки робити **лише на копії репозиторію**. Спадкові golden не змінювати (знято з незміненого коду); змінювати лише golden власних тестів і лише свідомо.

## 6. Відомі пастки (з досвіду)
- Тести зелені під root, червоні на CI: писали в реальні `/dev`, `/home`; завжди ганяти як `nobody`.
- `pkill -f <шаблон>` може вбити власну оболонку (шаблон збігається з командним рядком).
- Скрипти, що `source`-ять `gs/lib/*.sh`, ламаються без бібліотеки: `install.sh` має копіювати `lib/`.
- `set -x` у `build.sh` друкує розкриті секрети: `set +x` перед паролем.
- Глобальний git-конфіг (`commit.gpgsign`) робить SHA тестових репозиторіїв нестабільними: `GIT_CONFIG_GLOBAL=/dev/null`.
- Golden заморожують поведінку, не доводять коректність (аудит: 5 з 10 мутацій виживають): додавати цільові тести для гілок, які мігрували.
- GitHub API/raw з сесії інколи 403: піни в `build/versions.env` лишаються порожніми, обходу немає.
- Диск обмежений (~27 ГБ вільного), 4 ядра: тимчасові артефакти класти в `/tmp/<робочий-каталог>` і чистити; `*.whl` не коміттити.
- Копія для прогону як `nobody`: повна (`git ls-files -co --exclude-standard | tar cf - -T - | tar xf - -C /tmp/X`) і `chown -R 65534:65534`; неповна чи читабельна лише для читання копія дає хибні FAIL (запис `__pycache__`, відсутні `tests/lib`).
- Golden з числами з плаваючою комою залежать від платформи (libm): округлювати до значущих цифр, нулювати шум округлення, рівні значення впорядковувати за ключем. Перевіряти на справжньому раннері CI, не лише локально.
- Кілька агентів на спільних файлах (`tests/sim/fuzz/test_fuzz.py`, `mutations.py`, `docs/SIM-FUZZ.md`, `config/registry.tsv`, golden `config.out`): тільки інструмент Edit з унікальними рядками, ніколи read-modify-write усього файлу, `sed -i` чи `git stash`; зміни реєстру й спільних golden інтегрує лід.
- Новий скрипт змінює храповик літералів (`tests/static/config_scan.py`) і golden `config.out`: ідентифікатори помічати `# cfg-ok`, параметри виносити в реєстр.
- Звіт агента перевіряти: мої перші «FAIL» двічі були з моєї копії або пропущеного параметра (`--budget 40`), але реальні помилки знаходили саме незалежні прогони (D14, D17, портативність golden).
- Шари симуляції (`tests/sim/layers.sh`, ≈40 с) блокуючі в CI; нові шари додавати туди й до `docs/STATUS.md` §7.
